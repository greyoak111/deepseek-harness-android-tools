实验日期：2026-09-27
方法：两组对照实验，各 6 次连续运行，每次全新 prefix + 全新 wineserver

## 结论

### 1. 性能稳定，无退化

两组共 12 次运行，耗时集中在 **9.7 – 11.0 秒**，标准差极小。
连跑 6 次没有任何变慢趋势。

### 2. 不是内存泄漏

- `Slab` 恒定在 732–734 MB
- `PageTables` 恒定在 201–202 MB
- `MemFree` 反而逐次上升（227 → 630 MB）

### 3. 唯一的真累积：wineserver 数量

A 组里 wineserver 从 1 增到 6，**但每个只占 14 MB RSS**，无害。
B 组每次清掉，所以恒为 1。

### 4. 杀不杀 wineserver 对速度没有影响

A 组（不杀）与 B 组（杀）耗时区间重叠，无统计意义上的差异。

---

## 那么，之前观察到的 45s / 150s 是怎么来的

对比两组「慢」与「快」的实验环境：

| | A/B 测试（慢：10.9→45→150s） | 本次对照（快：稳定 ~10s） |
|---|---|---|
| 起始残留 | **有多个 wineserver，其中三个 VSZ 达 10–11 GB** | **彻底清场，0 残留** |
| prefix | 每次新建 | 每次新建 |
| 杀 server | 是 | A 组否 / B 组是 |
| FONTCONFIG | 已设 | 已设 |
| 库路径 | 已重排 | 已重排 |

**唯一实质差别就是起始残留。**

残留的 wineserver 占着 `.wine-<uid>/socket`，
新的 wine 启动后连上的是**陈旧的 server**，于是行为异常（慢、或看起来挂住）。

---

## 由此修正的几条判断

| 曾经认为 | 实际 |
|---|---|
| wine 会挂住 | **不会** —— 是残留 server 造成的 |
| box64 有缺陷需修 | **不需要** —— 干净环境下 12/12 成功 |
| 需要修 `statx` 或打补丁 | **不需要** —— 上游 #3813 已修，#4285 本机不适用 |
| 反复杀 wineserver 会更干净 | **不必要** —— 杀不杀都一样快；关键是**别留残骸** |

## 保留下来的真实成果

1. **三个性能坑**（fontconfig、库路径顺序、清理锚点）—— 实打实，18 秒 → 1 秒
2. **六个路径/loader 补丁** —— 缺一不可
3. **正确的使用方式**：`HODLL=libwow64fex.dll`、复用 wineserver、运行前清场
4. **CI 构建管线** —— 绕过安卓不能做 PE 交叉编译的限制

## 教训

**性能波动先怀疑自己的运维操作，再怀疑软件。**
本次一度把残留进程造成的劣化，误判为 wine 与 box64 的缺陷，
并据此去查上游 issue、打补丁、设想修 `statx` —— 全是在错误方向上用力。
